# sla-task-firstreply

Local automation that watches the Cloud Security Alliance IT-Operations Zendesk queue for tickets awaiting a first reply, drafts a fixed acknowledgment template for each one, and lets you review and edit every draft, then post it as a public reply or an internal-only comment, before anything is ever posted. Runs entirely on this machine via `launchd` — no dependency on a cloud scheduler or a live Cowork session for day-to-day operation.

## How it works

Two independent `launchd` services, plus a shared JSON file between them:

- **`scripts/first_reply_check.py`** — runs every 2 minutes during business hours (Mon–Fri, 9am–4pm local), looking back up to 72 hours (`ZENDESK_LOOKBACK_HOURS`) for candidate tickets, so a stretch with this Mac asleep or shut down doesn't create a blind spot. Pulls recent IT-Operations tickets from Zendesk, filters to ones with no public reply yet, drafts the acknowledgment text, and adds new candidates to `scripts/output/pending_drafts.json`. It never posts anything to Zendesk — detection and drafting only. Fires a native macOS notification, titled with a "CSA" prefix so it's identifiable at a glance, when something new shows up — with a sound (`ZENDESK_NOTIFICATION_SOUND`, default `Glass`) — or when the check itself is broken (throttled to once an hour).

  Notifications go out through up to three independent paths every time: [terminal-notifier](https://github.com/julienXX/terminal-notifier) (if installed via `brew install terminal-notifier`), a plain AppleScript banner, and — if you've done the one-time setup below — a small helper `.app`. This is deliberate redundancy, not an oversight: on at least this machine, neither terminal-notifier nor plain osascript reliably shows a banner when `launchd` triggers them in the background, even though both report a clean, successful exit every time with no error at all. A headless `launchd`-triggered process and an interactively-typed Terminal command get treated as different, separately-permissioned senders by macOS's Notification Center — confirmed directly by comparing a manual Terminal run (worked) against the identical command run via `launchctl submit` (silent). Firing all available paths means whichever one this Mac is actually willing to display still gets through. If terminal-notifier is installed, its banner is click-through (jumps straight to the review page); neither of the other two is. Every attempt's exit code and any error text is logged (`scripts/output/first_reply_check.log`), so if notifications are still silent, that log — not just "did an exception get thrown" — is the next place to look; a permission-denied-style message there points at System Settings → Notifications rather than at this code. See "Notification helper app" below for why the third path exists and how to set it up — it's the one most likely to actually work from a headless launchd context, since real `.app` bundles get their own row in Notification settings regardless of what launched them. (A custom CSA-logo notification icon was tried and dropped — modern macOS ignores third-party notification icons from CLI tools for security reasons, so it never actually rendered.)
- **`scripts/review_server.py`** — a small local-only web server at **http://127.0.0.1:8765/**, kept running continuously (`KeepAlive`). This is the only piece that can actually post a comment to Zendesk, and only when you click **Public Reply** (visible to the requester) or **Internal Comment** (agent-only) on a specific ticket, optionally after editing the draft text yourself. Also has a manual **Refresh from Zendesk now** button (runs the same detection logic on demand, bypassing the business-hours check) and a self-service **OAuth reconnect** flow at `/reconnect` for when the Zendesk token needs renewing.

Both scripts share config and logic through **`scripts/_common.py`**, so the two can't quietly drift apart — a real bug earlier in this project's life was caused by duplicated logic doing the same thing two slightly different ways.

## Setup

**Prerequisites:** the sibling `zendesk-mcp-server` repo checked out with its own `.venv`, with `zendesk_mcp_server` installed into it (`pip install -e .`) alongside `zenpy`, `requests`, and `python-dotenv`. This repo's `launchd` plists point at that venv's Python directly rather than duplicating it.

**Config:** copy `.env.example` from `zendesk-mcp-server` as a starting point, or use this repo's own `.env` (already git-ignored, never committed). One field is deliberately unusual: `ZENDESK_OAUTH_TOKEN_PATH` here is set to an **absolute path** pointing back at `zendesk-mcp-server/.zendesk_oauth_tokens.json`, not a local copy — that file is also read and refreshed by `zendesk-mcp-server`'s own MCP server (the live Zendesk connector used in Cowork sessions), so both consumers deliberately share one token file rather than risking two independently-refreshing copies drifting apart.

A few more optional knobs, all with sensible defaults so you only need to touch them if you want something different: `ZENDESK_REVIEW_PORT` (default `8765`), `ZENDESK_NOTIFICATION_SOUND` (default `Glass` — any name from `/System/Library/Sounds`, or empty for a silent notification), `ZENDESK_LOOKBACK_HOURS` (default `72`), `ZENDESK_NOTIFIER_APP_PATH` (default `~/Applications/CSA Notifier.app` — see "Notification helper app" below), `SLA_AGENT_NAME` (default `Catherine Vee` — whose activity the `/sla` page's personal charts are scoped to; must match the display name `sla-report-slack` recorded them under), and `IT_SECURITY_COLUMN_LIMIT` (default `5` — how many recent IT-Security tickets the `/security` page's read-only list shows; the name predates that page moving out of the main page's own layout column, kept unchanged so an existing `.env` setting doesn't silently stop working).

**For My tasks' "IT-Operations" Assignee/Requester option:** add `ZENDESK_IT_OPERATIONS_EMAIL=...` to this repo's own `.env`, set to the email address of the shared/departmental Zendesk account "IT-Operations" should resolve to. This is deliberately a real user account, not the existing `IT_OPERATIONS_GROUP_ID` group already used elsewhere for candidate-ticket routing -- Zendesk's `requester_id` field requires an actual user id, a group can't satisfy Requester at all, so Assignee uses the same real-user lookup (`resolve_it_operations_agent_id`) for consistency between the two fields. If this variable is left unset, choosing "IT-Operations" for either field on the promote form fails with a clear on-page error rather than silently falling back to something else; choosing "Catherine Vee" (the default) is unaffected either way.

**For the `/sla` page's "Check for newer data" button:** no extra setup needed beyond this Mac already having working git access to the `sla-report-slack` repo (the same access you'd need to `git pull` it by hand) — the button just runs `git pull --ff-only` there. It never touches Zendesk or Gmail itself, so it needs none of their credentials.

**For the `/sla` page's "Run full refresh" button (optional):** this one needs a GitHub personal access token, since it actually triggers `sla-report-slack`'s own GitHub Actions workflow rather than just reading what's already there. Add `SLA_REPORT_GITHUB_TOKEN=...` to this repo's own `.env` — a classic PAT needs the `repo` scope if `sla-report-slack` is private (or `public_repo` if it's public), a fine-grained token needs "Actions: Read and write" scoped to just that repo. Generate it yourself at github.com/settings/tokens and paste it into `.env` directly; never share the token value in chat. If `SLA_REPORT_GITHUB_TOKEN` isn't set, the button still appears but fails with a clear on-page message when clicked, rather than breaking anything else. `SLA_REPORT_GITHUB_REPO` (default `cvee-csa/sla-report-slack`) is also overridable if that repo's owner/name ever changes. Clicking this button no longer blocks the page for however long that workflow run takes -- it starts in the background and returns immediately, with a small status line under the buttons that updates on its own (polling every few seconds) once the run actually finishes, then reloads the page so the refreshed numbers show up without you needing to do it by hand.

**For the `/standup` pages:** no extra setup if the separate, private `meetingnotestool` repo is cloned at `~/Desktop/git/meetingnotestool`. This tool reads that project's built `dist/standup_data.json`, and writes only its `decisions.json` when you click one of the page's decision buttons. Set `STANDUP_DATA_FILE` in `.env` if it lives somewhere else. Without that file, `/standup` shows why and every other page keeps working.

### Notification helper app (one-time setup, optional but recommended)

On at least this machine, neither `terminal-notifier` nor plain `osascript` reliably shows a banner when triggered by `launchd` in the background — both exit cleanly (no error at all) but macOS silently drops the notification, apparently because a raw command-line binary launched headlessly isn't tracked as an approvable notification sender the way a real application is. A small Automator "Application" fixes this, since real apps get their own row in System Settings → Notifications regardless of what launched them. This is a one-time, few-minutes GUI setup:

1. Open **Automator** (Spotlight → "Automator"), choose **File → New**, and pick **Application** as the document type.
2. In the actions library on the left, search for **"Run AppleScript"** and drag it into the empty workflow area on the right.
3. Select all the placeholder code in that action and replace it with the contents of `scripts/csa_notifier.applescript` from this repo (delivered alongside this README — copy it in verbatim). If you ever move this repo to a different path, update the `payloadPath` line near the top of that script to match.
4. **File → Save**, name it `CSA Notifier` (Automator adds `.app`), and save it to `~/Applications` (create that folder in the save panel if it doesn't exist yet). This path is the default `ZENDESK_NOTIFIER_APP_PATH` — if you save it somewhere else, set that variable in `.env` to match.
5. Test it by double-clicking `CSA Notifier.app` in Finder once. You should see (and hear) a "CSA Notifier — Ready" banner — this exercises the exact same `display notification` call the real thing uses, just with placeholder text (there's no ticket payload yet). If macOS prompts you to allow notifications, approve it. Then check System Settings → Notifications for a "CSA Notifier" entry and make sure it's allowed with an alert style other than "None".
6. That's it — `first_reply_check.py` already knows to look for the app at that path and will use it automatically (see `notify()`'s third delivery path) once it exists; there's no code change needed on your end beyond building the app itself.

If you skip this step, the tool still works exactly as before — it just falls back to terminal-notifier/osascript only, which may or may not actually display anything depending on your Mac's notification permissions for headless processes.

**Install the services:**

```
cp scripts/com.csa.zendesk-first-reply-check.plist ~/Library/LaunchAgents/
cp scripts/com.csa.zendesk-review-server.plist ~/Library/LaunchAgents/
launchctl load ~/Library/LaunchAgents/com.csa.zendesk-first-reply-check.plist
launchctl load ~/Library/LaunchAgents/com.csa.zendesk-review-server.plist
```

`scripts/reload_launchd.sh` does the copy/reload steps for you (safe to re-run) — handy after pulling changes to this repo.

**After changing any script:** unload and reload the relevant plist so `launchd` picks up the new code:

```
launchctl unload ~/Library/LaunchAgents/com.csa.zendesk-first-reply-check.plist
launchctl load ~/Library/LaunchAgents/com.csa.zendesk-first-reply-check.plist
```

## Day to day

Open **http://127.0.0.1:8765/** any time to see what's waiting on you. Each card shows the ticket subject (badged **TEST** if it's a `[Test]`/`[Tooling]`-tagged ticket, and badged with **HIGH**/**URGENT** if Zendesk's own priority field is set to either -- already included free in every ticket payload, just not surfaced before; `normal`/`low` priority isn't badged at all, to avoid a badge on literally every single card for the common case), a resolved requester name (resolved directly from Zendesk by id where possible, with a flag explaining why if it couldn't be confirmed — worth reading before posting, since first-name collisions are real), the requester's original ticket text in full (not a truncated preview — long descriptions scroll within their own box instead of being cut off with "..."), and an editable draft, which now always opens with **"Hey _name_!"** -- addressing the requester by name (or "Hey there!" on the rare ticket where a name couldn't be confirmed) rather than the earlier rotation of a few interchangeable greetings, since naming the actual person is the point, not variety for its own sake. Pick **Public Reply** to post the draft where the requester sees it, **Internal Comment** to leave it as an agent-only note instead, or **Remove** to pull it from the queue without posting anything to Zendesk at all (a confirmation prompt guards against an accidental click, since this is permanent from this tool's side — a removed ticket won't be re-detected later even if Zendesk still shows no reply on it; if it still needs one, handle it directly in Zendesk).

The page follows your Mac's light/dark appearance setting automatically via `prefers-color-scheme`, and new cards fade in slightly on load rather than popping in abruptly. An **Auto / Light / Dark / B68FBF** control in the header lets you override that if you ever want this page in one mode regardless of your system setting -- your choice is remembered per-browser (via `localStorage`, not written to any file this tool tracks) and survives reloads and restarts; **Auto** clears the override and goes back to following the system setting. Button colors are deliberately not the usual red/green traffic-light convention — each action (Public Reply, Internal Comment, Remove, Refresh) has its own distinct hue instead, so nothing here relies on red meaning "bad" or green meaning "good" (the auth-connection warning banner uses amber, not red, for the same reason). **B68FBF** is a fourth, custom theme built entirely from the literal hex color `#B68FBF` and shades/tints of it, in place of the CSA-blue accent the other three modes share -- every background, text, border, link, and focus ring in that mode is derived from that same purple hue. It's the one deliberate exception to the "each action gets its own distinct hue" rule just above: instead of six unrelated hues, the six action buttons split evenly between two complementary shades -- `#B68FBF`'s own hue (Remove, Approve, Refresh) and its 30°-rotated sibling `#9E8FBF` (Reject, Internal, Claim), which shares B68FBF's exact lightness and saturation, so the two read as one deliberate family rather than an arbitrary second color. The amber warning/alert colors (the auth-connection banner, the already-replied flag) are left unchanged in B68FBF too -- those are functional caution signals, not CSA branding, and folding them into the purple family would make them blend in instead of standing out.

The logo/title, the Refresh button, and the pending/posted-today counts (shown as small pill-shaped stat chips) with the live "last checked"/"next check" countdown are all one merged header band (not two separate stacked bars) that stays pinned at the top as you scroll a longer queue, with a blue accent line under it tying it to the rest of the page's palette and a soft frosted-glass blur showing through from whatever's scrolled underneath (falls back to a plain solid background on any browser that doesn't support `backdrop-filter` — nothing breaks there, it just looks flatter). The browser tab picks up the CSA logo as its favicon and matches the on-page heading text.

Clicking any button anywhere on the page — Public Reply, Internal Comment, Remove, Refresh, or the reconnect-flow buttons — immediately disables it and swaps its label to a short in-progress message ("Posting…", "Refreshing…", etc.) so a slow connection never leaves you wondering whether the click registered or invites a second, duplicate click. It resets on its own the moment the resulting page loads, since nothing about it is persisted. Each draft textarea also accepts **⌘Enter** (Mac) / **Ctrl+Enter** as a shortcut for posting that draft as a Public Reply without reaching for the mouse — a small hint under the textarea is a reminder of the shortcut.

Two independent checks guard against someone else already having replied to a ticket before you act on it here — a real scenario this tool ran into ([ticket #156320](https://cloudsecurityalliance.zendesk.com/agent/tickets/156320) got a reply from someone else while it sat pending). First, every scan (the 2-minute cron tick, or a manual Refresh) re-checks every currently-pending ticket's Zendesk comments, not just newly-detected ones — if someone else's public reply shows up, that ticket is pulled from the queue automatically and you're notified, without you needing to click anything. Second, as a last-second safety net, the server re-checks a ticket's comments again right at the moment you click Public Reply or Internal Comment, in case the reply landed in the gap between the last scan and your click. Both checks fail open on a transient API error (logging why) rather than blocking a post over a brief hiccup, and both recognize a reply from *this tool's own configured Zendesk account* as an existing reply even on a self-created test ticket where the requester and the replying account happen to be the same person — without that, a self-answered test ticket would look identical to "the requester talking to themselves" and keep getting flagged as unanswered forever (this was a real bug: [ticket #156314](https://cloudsecurityalliance.zendesk.com/agent/tickets/156314) kept re-appearing as a "candidate" on every scan despite already having a reply).

The first check (the per-scan sweep) still acts automatically, since there's no click to gate on — a pending ticket someone else already answered is silently pulled out and you're notified. The second (click-time) check is different: if it finds an existing reply, clicking **Public Reply** or **Internal Comment** no longer posts (or skips) automatically — it shows a confirmation page with the reason ("a public reply already exists on this ticket...") and asks you to explicitly choose **Yes, post anyway** or **Remove instead (don't post)**, so posting on top of someone else's reply is always something you decided in that moment, not something this tool assumed on your behalf either way. If you want neither, just navigate back — the ticket stays pending, untouched.

A separate, purely informational badge covers the gap *before* any reply exists: a ticket can be sitting in Zendesk with a human colleague already assigned to it — actively working the underlying issue — even though nobody has posted the actual first reply yet, so it still shows up here as an unanswered candidate ([ticket #156391](https://cloudsecurityalliance.zendesk.com/agent/tickets/156391), an Employee Status Change request, is a real example of this). When a pending ticket's Zendesk Assignee is set to anyone other than this tool's own configured account, its card shows **"Also being worked on in Zendesk — currently assigned to _name_."** in the same amber warning styling as the already-replied notice, and its draft box renders empty (with a placeholder explaining why) instead of pre-filling the usual acknowledgment template — so a reply only ever goes out on one of these if you deliberately type one in, nothing gets sent on autopilot over a colleague's ticket. The stored draft itself isn't touched, just what's shown here; if the assignee is later cleared, the original auto-drafted text reappears. Unlike the already-replied notice, this one doesn't gate or block anything — Public Reply and Internal Comment still work normally, just with an empty starting point — it's context for you to weigh before deciding whether replying here would duplicate a colleague's work in progress. The assignee shown is refreshed on every scan (cron tick or manual Refresh) the same way the already-replied check is, so the badge (and the empty draft box) reflect whether someone has since claimed the ticket (or dropped it) in Zendesk directly, not just what its state was when the draft was first queued.

Since a posted (or skipped-as-already-handled) ticket's card disappears from the list, a confirmation banner echoes back exactly what happened — the text that was sent, or the reason nothing was — with the ticket's Zendesk URL rendered as an actual clickable link (not just plain text) so jumping over to see it there is one click, not a copy-paste. That's the record of what happened, not just a generic "done." A status bar up top shows pending/posted-today counts, plus two live-ticking values: how long ago Zendesk was last checked, and how long until the next automatic check — both count up/down in the browser every second via a small inline script, no page reload needed to see them move. The "next check" figure is an exact countdown to a resume time if you're outside business hours, or a rough estimate otherwise (launchd's timer isn't precisely predictable from outside the process, so that one is prefixed `~` as an honest approximation, not a precise countdown).

A collapsed **Replied today (N)** section sits below the pending queue (only appears once you've actually posted something today) — click it to see every ticket you've replied to today, most-recent first, each with its subject, a clickable link, whether it was a Public Reply or Internal Comment, and the clock time it went out. This is scoped specifically to tickets **you** replied to through this tool — it deliberately excludes Removed tickets and ones auto-pulled from the queue because someone else already handled them, since neither of those is something you actually sent a reply for. Whether you leave that section open or collapsed is remembered per-browser (the same `localStorage` pattern as the Auto/Light/Dark control) and survives reloads, so it doesn't spring back shut every time the page auto-refreshes.

A **Recently worked on (30)** column sits to the left of the pending queue, always visible rather than collapsed — the same idea (subject, link, Public Reply vs. Internal Comment, when it went out, and the same confirmed-requester avatar the queue cards use), but scoped to your most recent replies regardless of which calendar day they went out, rather than resetting at midnight like Replied today. It used to be a separate collapsed **Last N replies** section (capped at 10) sitting below the queue instead — folded into this wider, always-visible column instead of keeping both, since on a normal day the two were showing nearly the same tickets. The column is wide enough that most subjects fit on one line, with a longer one wrapping onto a second rather than getting cut off with an ellipsis.

This column now also picks up replies you sent **directly in Zendesk**, bypassing this tool entirely — not just ones sent through the Public Reply/Internal Comment buttons here. `_common.fetch_recently_worked_on` merges your local reply history with a live scan of the IT-Operations group: any recently-updated ticket this tool doesn't already have a local record of gets checked for a comment authored by your own configured Zendesk account, and if one's there, it's merged in at its real timestamp. A small muted note appears under the heading on the rare occasion this can't run to completion — either Zendesk isn't reachable right now (falls back to showing your local history alone, the same as this column always used to work) or the scan hit its own per-load budget (`WORKED_ON_COMMENT_CHECK_LIMIT`, 40 by default) before finishing — so a gap reads as "might be missing something," never as "there's nothing more." One known simplification: a ticket already in your local history is never re-checked against Zendesk, so a *later* direct-in-Zendesk reply on a ticket you'd already replied to through this tool won't move it to a newer time here — see `fetch_recently_worked_on`'s own docstring if that ever needs revisiting.

A new **IT-Security** page (`/security`, linked from the header nav) shows that group's 5 most recent tickets (any status — this isn't filtered to "awaiting a first reply" the way the main queue is, it's just a recent-activity snapshot, like [ticket #155814](https://cloudsecurityalliance.zendesk.com/agent/tickets/155814)). Each entry shows its subject, status, requester, and current Zendesk assignee ("Unassigned," "You," or a colleague's name), with a **Claim** button next to any ticket not already assigned to you. This page is read-only otherwise — no drafting, no reply actions, no already-replied checks — it exists purely so you can see what's recently come into that queue and grab one to work on without switching over to Zendesk first. This used to be a second column squeezed in alongside the main pending queue; it moved to its own page so the main queue reads as one focused list regardless of whether you're currently interested in IT-Security's own activity.

**Claim** also appears on every card in the main pending queue, right alongside Public Reply/Internal Comment/Remove, whenever that ticket isn't already assigned to you — including tickets flagged "Also being worked on in Zendesk," so you can knowingly take one over rather than just being warned about it. Claiming an unassigned ticket happens immediately; claiming one assigned to someone else asks you to confirm first ("This ticket is currently assigned to _name_ in Zendesk — claim it for yourself instead?"), since taking over a colleague's ticket is a bigger deal than grabbing an unclaimed one. Either way it's just a normal Zendesk assignee change — the same thing as reassigning it by hand in Zendesk's own UI — so it isn't gated behind anything heavier than that one confirmation. Claiming a ticket from the pending queue updates its badge and draft box immediately; claiming one from the IT-Security page only changes Zendesk itself, since that page doesn't track local state — its own cache picks up the change on its next refresh (see Design principles, below). Whichever page a Claim button is clicked from (main queue, /security, or /flagged), you land back on that same page afterward rather than always bouncing to the main queue.

One caveat on the full-text change: it only applies to newly-detected tickets going forward. A ticket already sitting in your pending queue from before this update was drafted (and cached) with the old truncated text, and that cached copy doesn't get rebuilt until you post it — so if you still see a "..." cutoff on an existing card, that's why; it'll be gone for anything detected from now on.

The page also quietly reloads itself every 60 seconds, so a ticket the background cron just detected shows up without you needing to hit your browser's reload button. This is just a local re-render of the current pending-drafts file, not a fresh Zendesk scan — it skips reloading (rather than clobbering it) if you're mid-edit in any draft's textarea.

If the Zendesk connection needs attention (expired token, etc.), an amber warning banner appears with a **Reconnect now** link — click it, approve access in the browser tab it opens, then paste the URL you get redirected to back into the page. No Cowork session required for this.

A **SLA metrics** link sits in the header next to Zendesk OAuth, opening a new **/sla** page that summarizes IT-Operations SLA compliance — today's totals (open, breached, due soon, on track, compliance %), a week-over-week trend for breached/due-soon/total-open (arrow-and-percent, only shown once 14+ daily snapshots exist to compare two full weeks), and the ticket ids currently in breach with a by-rule breakdown. This isn't computed here — it's read directly from the separate `sla-report-slack` repo's own `data/sla_history.json`, a 90-day rolling history that repo's own GitHub Actions job appends to once a day on weekdays (see that repo's README). Because of that, the numbers are only as fresh as this Mac's last `git pull` of that sibling repo, not live — the page always shows the snapshot's actual date, and flags it explicitly if it's more than a few days stale (beyond a normal weekend gap). A link at the bottom opens that repo's own full multi-chart `sla_dashboard.html` directly from disk (a `file://` link, since this server has no static-file route) for the deeper agent-activity/rule-breakdown charts this page doesn't try to reproduce. If `sla-report-slack` isn't checked out as a sibling folder next to this repo, or hasn't run yet, the page says so plainly instead of erroring.

Below the team-wide numbers, a **Your activity — Catherine Vee** section (configurable via `SLA_AGENT_NAME`) charts one person's own reply activity and solved-ticket count over the full history: a stacked bar chart of public replies + internal comments per day, and a bar chart of tickets solved per day, plus running totals for the window. This is the one part of the /sla page that's genuinely personalized, because it's the one part of `sla_history.json` that's actually tracked per-agent per-day (`agent_activity` and `solved_by_agent`) -- the queue-health and violations-by-rule numbers above stay team-wide, since that file has no historical record of which agent a given ticket was assigned to on a given day, only who replied to or solved it. A day that never recorded per-agent data at all (this has happened for a handful of recent runs -- see that repo's own history) renders as a dim gray hairline rather than a bar, so "genuinely zero replies that day" and "we don't actually know" don't look identical. The two charts are plain inline SVG built server-side -- no Chart.js, no CDN, no client JS required for them to render correctly, matching this file's existing self-contained-page philosophy -- with a native browser tooltip (hover any bar) showing the exact numbers for that day. That's a real tradeoff against the CDN dashboard's own pan/zoom/live charts, made deliberately rather than by default: this is a small personal supplement to the team view, not an attempt to fully reproduce that page here (the "Open the full dashboard" link above still exists for that).

A visual pass followed once the page had grown to three pages and two columns: every action (Public Reply, Internal Comment, Remove, Refresh, Claim, and the two header nav links) now has a small inline icon next to its label, and only one action per page is a solid filled button -- Public Reply on the main queue, Complete Reconnect / Start Zendesk Reconnect on the OAuth page -- with everything else (Internal Comment, Remove, Claim, Start over) rendered as an outlined button that only fills in on hover, so the primary next step reads as more prominent than the rest instead of every button competing at equal weight. The confirmation banner is now a toast that floats in the bottom corner and fades itself out after a few seconds, rather than a bar docked above the queue that stayed until the next reload; the amber "Zendesk connection needs attention" warning is unaffected by this and still stays put in the normal page flow, since that's a standing condition rather than a one-off event. Ticket cards got a bit more visual hierarchy (a small "TICKET" label above the number, a slightly larger/bolder subject line), a flatter default look (border only, no permanent shadow -- a subtle shadow now appears only on hover, as a lift rather than a constant), and a colored initials bubble next to any requester/assignee name this tool is actually confident in (never next to a guessed or unconfirmed name, since that would lend it false certainty). The **Zendesk OAuth** / **SLA metrics** links moved out of the meta status line and into their own small icon-button group in the header, next to the theme toggle, so they read as navigation rather than trailing off the end of a sentence. The `/sla` page's "Today" numbers are now proper KPI tiles (big number, small label, a colored left edge hinting at good/neutral/bad) instead of the small pill-shaped stat chips, which are still used where they were always a good fit -- the compact pending/posted-today counts in the header. Clicking any per-ticket action now also fades that card out immediately (alongside the existing button-disables-and-relabels behavior) for a snappier feel while the request round-trips -- this is a lightweight CSS transition triggered on submit, not a real optimistic local-state update; the server-rendered reload afterward is still what actually removes the ticket.

Sitting right next to it is a second, visually distinct button: **Run full refresh** (gold, versus the pull button's blue). Because that workflow's "Run SLA report" step hardcodes `DRY_RUN: "false"` no matter how it's triggered, clicking this button **does** cause a real Zendesk scan and **does** send `sla-report-slack`'s own daily email -- both stated on the page, not just here. It also needs a different kind of credential than the pull button: a GitHub personal access token (`SLA_REPORT_GITHUB_TOKEN`, see Setup above) instead of Zendesk/Gmail secrets, since the actual Zendesk/Gmail work still happens inside `sla-report-slack`'s own GitHub Actions run, using its own GitHub Secrets, never read or copied by this project. ## Design principles

- **Nothing posts to Zendesk without a human clicking Public Reply or Internal Comment.** The cron script can only read and draft; only the review server can write, and only on an explicit click. Removing a ticket via the **Remove** button is the one queue action that doesn't post anything at all -- it only stops this tool from tracking that ticket.
- **Every candidate stays on the page until you act on it, you remove it, or Zendesk itself resolves the question for you.** Post it publicly, post it as an internal note, remove it, or leave it pending. The one fully-automatic exception is the per-scan already-replied sweep: if someone else beats you to the actual first reply while a ticket sits pending, the next scan notices and pulls it from the queue on its own -- that's Zendesk's own state overriding the queue, not an action you triggered. Clicking Public Reply or Internal Comment on a ticket that already has a reply is handled differently: rather than silently posting or silently skipping, it stops and asks you to confirm first (see "Day to day" above) -- an already-replied ticket only ever leaves the queue automatically via the scan sweep, or explicitly via your own click.
- **A queue mutation always re-checks the ticket's current status inside the same lock, never trusts what the browser last rendered.** The review page can be up to a minute stale (auto-refresh) or older if you leave a tab open; clicking Remove on a ticket that a background scan has since moved to `already_handled` (or that another tab already posted/dismissed) doesn't blindly overwrite that outcome -- it's left as-is, and you're told so, rather than the click silently discarding what actually happened.
- **A failed post leaves the draft intact.** Nothing is lost if Zendesk is briefly unreachable or the token needs reconnecting.
- **No bulk actions.** Every reply gets individually reviewed — a "select all, post" button would defeat the point of the review gate.
- **Localhost only, no login.** The review server binds to `127.0.0.1` and is never reachable off this Mac. There's no additional auth layer on top of "you're logged into this machine," which is an intentional tradeoff for a single-user local tool, not an oversight.
- **A nav badge is for "does this need a look," not just "here's a number."** Blocked/Standup, IT-Security, and My tasks all carry a count badge because that count is itself a signal worth noticing at a glance. Recently Solved deliberately has none: its count just climbs toward `RECENTLY_SOLVED_LIMIT` as its cache warms and says nothing about whether anything there needs attention -- a badge on it would be decoration wearing a signal's clothes.
- **A basic accessibility pass, not a full audit.** The confirmation banner is announced to screen readers as it appears (`role="status" aria-live="polite"`), the ticket queue sits inside a `<main>` landmark for skip-to-content navigation, and the requester-name-confidence flag text was checked against its background and comfortably clears WCAG AA contrast (4.5:1) in both light and dark mode. This is a single-user local tool first, so it hasn't had a full screen-reader/keyboard-only pass, but the low-effort wins are in.
- **The "also being worked on" assignee badge is informational only, never a gate.** It costs one extra `get_ticket` call per currently-pending ticket on every scan (to keep the badge current) -- a deliberate small cost against the IT-Ops queue's normal size, not something that scales badly, but worth naming as a tradeoff. Unlike the already-replied check, it never blocks or delays a post, and never pulls a ticket out of the queue on its own -- Zendesk's Assignee field can be wrong, stale, or set for reasons that have nothing to do with someone actually working the ticket, so this tool treats it as a hint for the human reviewing, never as ground truth it acts on unilaterally.
- **The IT-Security page (and /flagged) are cached, unlike the main queue.** `GET /` used to never touch Zendesk at all -- it only read the local `pending_drafts.json` file and a cached auth-status file, by design, so loading the page (including its own 60-second auto-refresh) never depended on Zendesk being reachable. That's now narrowed rather than true without exception: the Recently worked on sidebar's outside-the-tool discovery (`fetch_recently_worked_on`, see "Day to day" above) is the one thing on "/" that makes a live Zendesk call. It keeps the same spirit deliberately -- the local half of that sidebar's data is always computed first and returned on its own the instant anything about the live half goes wrong, so "/" still can't actually *break* over Zendesk being unreachable, it just quietly stops finding outside-the-tool replies until the connection's back. /security and /flagged break the "never touches Zendesk" rule more plainly: showing live tickets means an actual Zendesk API call somewhere, with no local-only fallback content to degrade to. All three -- /security, /flagged, and the worked-on sidebar's live half -- share the same caching shape: each result is cached in-process for 2 minutes (matching the cron scan's own cadence) and served stale-but-instant on a cache hit; if a refresh attempt fails (or Zendesk isn't connected), it falls back to the last successful result (or, for the worked-on sidebar specifically, to local-only data) rather than blanking the page. IT-Security was originally a column embedded directly in the main page, meaning this cache used to be the *only* thing standing between "/" and a live Zendesk call on every load; moving it to its own /security page kept that same caching, just relocated along with the page itself.
- **Claim is a plain Zendesk assignee change, not a new kind of action.** It's exactly what clicking the Assignee field in Zendesk's own UI and picking yourself does -- easily reversible, nothing posted, nothing destroyed -- so it doesn't get its own confirm-page interstitial the way an already-replied post does. The one exception is taking over a ticket that's currently assigned to someone else, which asks for an in-page confirmation first, since that's a bigger deal than claiming an unclaimed one.
- **The /sla page reads another tool's numbers rather than recomputing them.** SLA-breach classification (which thresholds, business-hours math, what counts as "due soon") already lives in `sla-report-slack`, which this repo doesn't depend on or import -- it just parses that repo's `data/sla_history.json` as sibling-folder JSON. Reimplementing that classification logic here, a second time, in a second file, is exactly the kind of duplication this project got burned by once already this session (the launchd OAuth-path bug); reading the one place that already computed it avoids a second copy that could quietly drift out of sync with the first. The tradeoff is that this page can only ever be as current as that repo's last local `git pull` -- it says so on the page itself rather than implying the numbers are live.
- **Only personalize what's actually tracked per-person.** The "Your activity" charts exist because `agent_activity`/`solved_by_agent` genuinely are recorded per-agent per-day in `sla_history.json` -- queue health and violations-by-rule aren't (no historical per-ticket assignee record), so those stay team-wide rather than being faked into a misleading "just for you" view. When a day's snapshot didn't record agent activity at all, the chart shows a dim gray marker, not a colored zero-height bar -- "not tracked" and "genuinely zero" are different claims and shouldn't look the same.
- **The personal charts are plain SVG, not a second charting library.** No CDN script, no client-side JS required for them to render correctly -- consistent with this server having no static-file route and every page being one self-contained response. The cost is losing the CDN dashboard's pan/zoom/live tooltips in exchange for a native-`<title>` hover tooltip instead; that's an accepted, deliberate scope limit for a small supplementary chart, not a first attempt at replacing the full dashboard link that still sits above it.
- **One primary action per page, everything else outlined.** Public Reply (or Complete/Start Reconnect, on the OAuth page) is the only solid-filled button anywhere -- Internal Comment, Remove, Claim, and Start Over all render as an outlined button in the same hue that only fills in on hover. Same six-color, non-red/green palette as before this pass, just used to carry less visual weight by default so the one filled button per page reads as the obvious next step.
- **Icons are a fixed, swatch-verified set, not an icon font or external library.** All seven glyphs (`_ICONS` in `review_server.py`) are hand-authored inline SVGs sized via CSS classes (`.icon`/`.icon-sm`) so they inherit whatever color the surrounding button or link already has -- no separate icon-color variables needed per theme. They were rendered in an actual browser and screenshotted before being wired into any button, the same "verify before shipping" standard as everything else here, rather than trusting hand-written path data to look right sight unseen.
- **A decorative topic icon and a functional button glyph are two different tiers, not one system stretched to cover both.** The `_ICONS`/`_icon()` glyphs above exist to sit inline in a button label and stay legible in either theme via `currentColor` on a transparent stroke path. Page headings, empty-state boxes, and the priority pill instead use `_topic_icon()` -- small PNGs pulled from the CSA Asset Repository's own brand icon library (`assets/topic-icons/`, inlined as base64 the same way `LOGO_DATA_URI` already was), each a self-contained colour badge with its own filled background baked into the file rather than `currentColor`. That's deliberate: a badge with its own background reads the same in light or dark mode without needing a per-theme icon-color variable, which a `currentColor` glyph would. The one spot that isn't a self-contained badge is the priority pill, which sits inside `.badge-priority`'s own colour fill already -- that one uses the plain white glyph-only variant instead of another badge-on-badge. Every topic icon's `alt` is deliberately empty (purely decorative, redundant with the visible heading/label text right next to it), and a missing file degrades to no icon at all rather than a broken-image box, the same fail-open pattern `LOGO_DATA_URI` already established.
- **The confirmation toast and the auth-warning banner share CSS but not behavior.** Both use the `.banner` class for color/shape, but only the confirmation toast (marked with `data-toast="true"`) floats in the corner and auto-dismisses after a few seconds -- the auth-warning banner overrides back to a normal, docked, non-floating block (`.auth-warning`'s CSS), since a standing "reconnect needed" condition shouldn't quietly disappear on its own timer the way a one-off "posted!" confirmation should.
- **The optimistic fade on submit is cosmetic, not a real optimistic update.** A ticket/mini-ticket card fades out the instant its form is submitted, purely via a CSS class toggled in the existing submit listener -- there's no local state being patched ahead of the server's response the way a true optimistic-UI implementation would do. The actual removal still only happens because the next server-rendered page doesn't include that ticket; if a post ever failed, the faded card simply reappears (unfaded) on the page the failure response renders, same as before this change.
- **Avatars only appear next to names this tool actually trusts.** The colored initials bubble (`_avatar_html`) is only ever called for a confirmed requester name or a real resolved assignee name -- never for an unconfirmed guess, which already carries its own "verify before approving" flag elsewhere on the card. Adding an avatar there would visually suggest more certainty than the tool actually has. This now extends to the **Replied today**/**Last N replies** rows too, via the same confirmed-only helper (`_requester_avatar_prefix`), so the trust cue is consistent everywhere a name appears rather than only on the live queue cards.
- **A legend explains a mark where the mark actually is, not lower down the page.** The /sla page's "not tracked that day" note renders as a color swatch plus one line, positioned directly under the chart whose gray hairlines it's explaining -- not as a paragraph of prose after both charts that requires remembering what you saw a few inches up. Same principle behind the page's shared date-range line: it states a fact that's actually true of the underlying data (both sections read the same `sla_history.json` entries) rather than asserting a unified "window" that would overstate how aligned team metrics and personal activity really are.
- **A date-range control only appears where a range is honestly meaningful.** The personal activity charts iterate over a variable-length window of daily snapshots, so a 7/14/30/90/All picker (`SLA_AGENT_RANGE_OPTIONS`) is a real, honest control there. "Today," "Week over week" (a fixed 7-vs-prior-7 comparison), and "Current breaches" (the latest snapshot) aren't rangeable in any meaningful sense, so they deliberately don't get one -- adding a picker to them would just be a control that doesn't actually control anything.
- **Selecting a chart range is a page reload with a query param, not a client-side redraw.** The range pills are plain `<a>` links to `/sla?range=N` -- picking one re-renders the whole page server-side, same as every other navigation here. This keeps the "no client JS required for correctness" rule intact rather than introducing a second rendering path (client-side re-drawing of already-sent chart data) that could drift out of sync with what the server would render for that same range.
- **"Refresh" costs exactly what it costs, stated on the page, not discovered after clicking.** The /sla page's "Check for newer data" button was built by first reading `sla-report-slack`'s actual `zendesk_sla_slack_report.py` end to end, not assumed from its README -- which is how it became clear that its `DRY_RUN` mode explicitly skips writing a new snapshot, so a direct-invoke version would have to send a live email on every click. Rather than accept that cost, the button was rebuilt around a plain `git pull --ff-only` instead (`_common.pull_sla_report_data`) -- no Zendesk/Gmail credentials, no email, at the honestly-stated cost of only ever showing data someone else has already committed. Whichever tradeoff a feature like this ends up making, it's stated plainly next to the control, not left for the user to discover after clicking.
- **Private data stays out of a public repo, even when a page here shows it.** `/standup` renders notes about colleagues from the private `meetingnotestool` project. This repo is public, so it holds only the rendering code: the data is read from that other checkout at request time (`_common.standup_snapshot`, mtime-cached), never copied, cached to disk, or used as a test fixture here. `scripts/tests/conftest.py` points `STANDUP_DATA_FILE` at a temp path and `STANDUP_DECISIONS_FILE` at temp paths, so no test can read the real notes or write a real decision.
- **A read-only dependency stays read-only, even for its own "refresh."** This tool never commits to `sla-report-slack` -- so its one write-adjacent interaction with that repo (`git pull --ff-only`) is deliberately restricted to fast-forwards only. If the local clone ever diverges (a stray local commit, a rebased remote history), the pull fails loudly with git's own error message rather than this function quietly creating a merge commit in a repo it doesn't own.
- **Two honestly different refresh buttons, not one button pretending to be simple.** "Check for newer data" and "Run full refresh" do genuinely different things at genuinely different costs (passive git-pull vs. triggering a real Zendesk scan + email), so they're two separate, visually distinct controls rather than one button whose behavior secretly depends on hidden state. A user picking between them should be able to tell what each one costs from the page itself, without needing to click and find out.
- **A new workflow gets a new page, not a bolt-on to an existing one.** My tasks lives at its own `/tasks` URL rather than a panel wedged into the main queue page, the same way SLA metrics already got its own `/sla` rather than crowding the ticket-triage view -- each page stays about one thing, and none of them has to reserve layout space for a feature most visits to it won't touch.
- **Exclude by what a ticket actually is, not by where it happens to live.** Personal tasks are kept out of the pending-reply queue via the `personal_task` tag (checked directly in `find_candidates()`), not by requiring them to land in some specific group -- Zendesk decides which group a new ticket gets filed under, not this tool, so a safety check that depended on a particular group id could silently stop working the moment that default changed. The tag travels with the ticket regardless.
- **A page's own status shouldn't require being on that page to see.** The SLA breach count, the My tasks count, whether Zendesk needs reconnecting, how many tickets are pending -- all four used to only be visible on the one page each belongs to. They're now small badges riding on the nav links (and the home link) that render on every page, all computed from the same cheap local files those pages already read -- no new Zendesk call was added anywhere just to make a badge current.
- **Jotting an idea and committing to a real ticket are two different actions, not one.** My tasks' "Add task" only ever saves a local draft -- creating the actual Zendesk ticket is a separate, explicit click (`promote_personal_task`). This replaced an earlier version where every add was immediately a real ticket, which made it too easy to end up with Zendesk tickets for things that were really just half-formed ideas. A draft can be discarded with no trace; a promoted task can't be un-promoted, only marked done -- the tool's own local state always matches whether a real ticket actually exists yet.
- **A draft can be fixed up or reshuffled right up until it becomes a real ticket, never after.** Edit and Move up/down (`edit_personal_task`, `move_personal_task_draft`) both refuse outright on a task that's already promoted, with a clear error rather than silently no-opping -- once a real Zendesk ticket exists, its subject/notes/order live in Zendesk, not in this local list, so letting either action succeed past that point would just create a second, quietly-diverging copy of the truth.
- **A value given early only ever pre-fills a value asked again later -- it never skips the ask.** Estimated minutes can optionally be given at draft time (on "Add task"), but the promote form still asks for it and still requires it -- the earlier value just saves retyping, since a rough guess jotted down while adding a task might not be what you actually want to promote with once you're looking at it again.
- **A field with a fixed, closed set of real values gets a `<select>`, not a free-text box.** Assignee, Requester, and Allocation are Zendesk-side identity/field values with a small, known set of valid options (two identities, two allocation values) -- rendering them as dropdowns pre-populated from `PERSONAL_TASK_IDENTITY_LABELS`/`PERSONAL_TASK_ALLOCATION_LABELS` makes an invalid choice structurally impossible from the UI, rather than relying on server-side validation alone to catch a typo a free-text field would have allowed.
- **Two fields that happen to often agree are still resolved independently.** Assignee and Requester both default to "Catherine Vee" and are commonly promoted that way together, but `resolve_personal_task_identity` is called once per field rather than once for both -- a task assigned to IT-Operations but requested by Catherine Vee (or vice versa) is a legitimate combination this tool shouldn't quietly prevent just because the common case has them matching.
- **A ticket's group and its individual assignee are two different things, and only one of them varies per task.** Every personal task ticket lands in the IT-Operations group -- it's IT-Operations work either way -- while the individual Assignee/Requester choice is what actually varies (Catherine Vee vs. the shared IT-Operations account). Making the group a fixed default rather than a fourth selectable field on the promote form keeps the form asking only about the one thing that's genuinely a per-task decision.
- **A file write either fully happens or doesn't happen at all.** `pending_drafts.json`/`personal_tasks.json` are now written via a temp-file-then-`os.replace()` swap (`_atomic_write_json`) rather than a plain `write_text()` -- `os.replace` is atomic on POSIX, so a crash or a full disk mid-write can never leave either file half-written. That matters specifically because `load_pending()`/`load_personal_tasks()` both fail open with a broad except-return-`{}` on a parse error -- without an atomic write, a torn file would silently make every tracked ticket/task vanish with nothing logged, not just fail to load once.
- **One predicate, not two copies that happen to currently agree.** `check_already_replied` (the click-time recheck right before posting) used to reimplement the exact same author-id comparison `_has_public_reply_from_other` (the detection-time check) already encapsulated, rather than calling it. Both now go through one shared `_first_public_reply_from_other` -- the two checks staying in sync is now structural, not just presently true by luck, which is exactly the kind of duplication this project has been burned by once before (the launchd OAuth-path bug).
- **A real Zendesk write needs a real guard against happening twice, not just a status check.** This server runs on a `ThreadingHTTPServer`, so a double-click before the button's own disable-on-submit JS fires (or a retried slow request) can genuinely land two overlapping requests for the same personal task. `promote_personal_task`/`complete_personal_task` couldn't just check-then-mutate inside `update_personal_tasks`'s file lock the way every other action here does, since holding that lock across a live `create_ticket`/`update_ticket` call would block every unrelated task mutation for however long Zendesk takes to respond -- so a small in-process guard (`_begin_personal_task_action`/`_end_personal_task_action`) closes the specific window between the unlocked "still a draft?" read and the eventual locked write, without serializing unrelated work behind a slow network call.
- **A transient failure isn't cached, but a real answer is.** `_resolve_agent_id_by_email` (behind `resolve_own_agent_id`/`resolve_it_operations_agent_id`) caches a resolved id for `AGENT_ID_CACHE_TTL_SECONDS`, the same TTL-cache treatment `fetch_recent_tickets` already gave the IT-Security column -- but only on a successful `search_users` call. A `search_users` exception returns `None` without being cached, so the very next call retries instead of being stuck reporting "unresolved" for the rest of the cache window over what might have been a one-off API hiccup.
- **A file that can hold a credential gets tightened, even on a single-user Mac.** `AUTH_STATE_FILE`, `OAUTH_PENDING_FILE`, and the shared OAuth token file (written by `zendesk_client.py`'s own methods, which this project doesn't modify) are all opportunistically `chmod`'d to `0600` (`_harden_file_permissions`) after being written -- a plain `write_text()` otherwise leaves a file at whatever the process umask allows, which could be group- or world-readable on a shared account. Best-effort and silent on failure, since a permissions tweak failing shouldn't break the feature it's trying to harden.
- **A guard against "twice" needs to cover every action that touches the same thing, not just the one that made it a real Zendesk write.** `promote_personal_task`'s in-process guard already stopped two overlapping promotes -- but `discard_personal_task`/`edit_personal_task`/`move_personal_task_draft` didn't take it at all, so a discard landing in the exact window between promote's own unlocked "still a draft?" read and its later write could delete the local draft out from under a ticket that was about to exist for real, orphaning it with no local record left. All three now take the same `_begin_personal_task_action` guard promote/complete/quick-solve already used. The equivalent gap existed for posting a reply/internal comment (`_post()` had no per-ticket guard at all, so a double-click could post the same reply to Zendesk twice) -- closed the same way, with its own separate `_begin_pending_ticket_action`/`_end_pending_ticket_action` guard keyed by ticket id rather than personal-task local id.
- **A file lock and a live network call are still two different things, even when one function happens to need both.** An earlier version of `reconcile_personal_tasks` ran its `get_ticket()` lookups from inside the very closure `update_personal_tasks` calls while holding `personal_tasks.json`'s exclusive lock -- meaning loading `/tasks` with a slow Zendesk connection could block someone else's add/edit/discard/promote/solve click for however long every open task's lookup took, combined. It now does the network reads on a plain, unlocked pass first, and only takes the lock afterward for the fast, no-network write (re-checking each entry is still exactly the state that decision was based on, since something else could have changed it in the meantime).
- **Escaping for a nested context happens in the order the browser actually undoes it, not the order it's easiest to write.** The Claim button's confirm() dialog embeds a Zendesk assignee's name inside a JS string literal, itself inside an HTML attribute -- two contexts, not one. Escaping only for the JS layer (backslash and single quote) and leaving a literal double quote alone let an assignee name containing one silently break out of the surrounding `onclick="..."` attribute, dropping the confirmation dialog with no error. The fix escapes for the JS layer first, then HTML-escapes the result -- matching the order the browser's HTML parser (which runs before the JS engine ever sees the string) actually decodes it back.
- **A required field can't just be left out at solve time the way it can at creation time.** A task promoted before Estimated minutes existed has none recorded, and creating its ticket correctly just omits that custom field -- but Zendesk rejects a *solve* missing any of the three IT Requests fields, so a legacy task like that couldn't actually be solved at all, silently, with no way to fix it from the page. Both solve forms now grow an inline, required Estimated minutes input specifically when the task has none on file, collecting it right at the point it's actually needed rather than failing later with nothing to act on.
- **A retried action can't re-do the part that already succeeded.** If Quick Solve's two comment posts succeed but the solve call after them then fails, the task is still "open" -- and without tracking that, clicking Quick Solve again to retry would post both comments a second time before even attempting the solve again. Each comment's posted-or-not state is now recorded on the task the moment it succeeds, independently of the solve outcome, so a retry only ever does the part that didn't already happen.
- **A page's header is a glance, not a dashboard.** A KPI-tile version of the main page's header (all five of `summary_counts()`, in the same bigger-number tile shape `/sla`'s own "Today" row uses) was tried and then explicitly reverted back to the original two small stat-chip pills ("N pending" / "M posted today") -- the tile treatment earns its size on `/sla`, where those numbers are the page's entire reason for existing; on the main page, they're a secondary status line sitting above the actual content (the ticket queue), and five big tiles pulled too much visual weight away from it. `_kpi_tile` itself stays a shared module-level helper either way, since `/sla` still uses it for its own tiles -- only the main page's header went back to plain pills.
- **A ticket's own "waiting" clock and Zendesk's "last touched" clock are two different facts, and only one of them was ever shown.** A pending ticket's card only ever showed how long *this tool* has been waiting on it (`created_at`, its own local first-seen timestamp) -- a ticket where a note got added or a field changed in Zendesk, with no reply yet, looked identical to one that's been completely silent the entire time. `build_drafts` now also captures Zendesk's own `updated_at` for a brand-new candidate (free in the exact same ticket payload `priority`/`assignee_id` already come from), and `recheck_pending_for_assignment` keeps it fresh every scan off the very same `get_ticket` call it already makes for the assignee badge -- no new Zendesk call anywhere. Rendering it reuses `_relative_age`'s own day/hour/minute bucketing (split into a shared `_duration_bucket` core) rather than a second copy of that threshold logic, since the only real difference between "waiting" and "updated ... ago" is the timestamp's source and format -- this tool's own naive-local clock for one, Zendesk's UTC "Z"-suffixed clock for the other.
- **The header's two rows now each answer one question, instead of one row answering all of them at once.** Logo/title/pending-badge, the one page-specific action button (Refresh, Reconnect, etc.), and the theme toggle all fit on row 1 ("who am I / what's the one thing to click here") with room to spare; the five nav links get their own row 2 underneath, so a full-width action button and a five-link nav group never again have to fight over the same strip of space and wrap unpredictably. Five smaller changes came out of that split: the header's stat-chip row dropped its "N pending" pill entirely, since that count was already shown a second time on the logo/title's own badge on every page -- only "M posted today" (which has no other home) stays there now. The theme toggle went from four text-labeled buttons to icon-only (new `sun`/`moon`/`monitor` entries in `_ICONS`, plus a literal `.theme-swatch` color chip for B68FBF, since that theme is an actual hex color, not a concept an icon could stand in for) -- a standing "set once and forget" preference doesn't need the same visual weight as actual navigation, so it's tucked into row 1's far corner instead of competing on the nav row. The nav row itself split into two `.top-nav-cluster`s with a `.nav-divider` between them: "is this healthy" status links (Zendesk OAuth, SLA metrics) read as a different kind of link from "take me to a workflow page" (My tasks, Blocked/Standup, IT-Security). And Zendesk OAuth specifically collapses to icon-only when `auth_ok` is true -- its full text label (and warning badge) only earn their space back when there's actually something wrong to say.
- **An easter-egg theme gets an easter-egg logo, swapped in pure CSS, not JS.** B68FBF replaces the CSA header logo with a small pixel-art mark (`assets/b68fbf-logo.png`, `LOGO_B68FBF_DATA_URI`) while that theme is active. Both logos are always in the rendered DOM (`.logo-default` / `.logo-b68fbf`); `html.theme-b68fbf`'s existing CSS override just toggles which one `display`s, the same class `theme_init_script` already applies before first paint to avoid a flash of the wrong *colors* -- reusing that mechanism means the logo swap gets the same no-flash guarantee for free, instead of a second JS-driven src-swap that could race with it or need its own separate early-`<head>` script.
- **Once a theme has its own identity, its swaps should be complete, not partial.** A follow-up pass closed five remaining gaps the logo swap above didn't reach, each riding the same infrastructure already in place rather than inventing a new mechanism per gap. The topic-icon badges (`_topic_icon()`) get their own B68FBF-recolored set (`assets/topic-icons/*-b68fbf.png`, generated by `recolor_topic_icons.py`, which hue-rotates each badge's baked-in CSA-blue background to B68FBF's own 288.75-degree hue while preserving its original saturation/value -- the same fixed-hue-varying-shade idea the theme's CSS custom properties already use for button colors, just applied per-pixel to a raster badge) -- `_topic_icon()` now renders both variants (`topic-icon-default`/`topic-icon-b68fbf`) and lets CSS pick the right one, the exact same trick the logo used; `priority-alert` (a plain white glyph with no badge background to recolor) has no B68FBF entry and correctly just renders its one image, unchanged, in every theme. The favicon now follows the logo swap too -- this one genuinely needs a few lines of JS, since a `<link rel="icon">` can't be duplicated and CSS-toggled the way an `<img>` can, so `theme_init_script` and the theme-toggle's `applyTheme()` both swap `href` off a `data-href-b68fbf` attribute the tag already carries, caching the tag's own original href into `data-href-default` the first time either script touches it rather than the server embedding that (already-duplicated-once) string a third time. A new `<meta name="theme-color">` follows the same two scripts' lead, computed from one small hardcoded mode-to-hex mapping (covering the live OS-preference case too, via `matchMedia`) rather than a set of static per-scheme tags that would still need a manual override for the two explicit non-system modes anyway. `::selection` and `scrollbar-color` needed nothing theme-specific at all -- both just read the existing `--accent`/`--bg` custom properties, so they already follow whichever theme is active for free. And the avatar-initials palette (`_AVATAR_HUES`) gained a B68FBF sibling (`_AVATAR_HUES_B68FBF`, generated into CSS by `_avatar_hue_css()` so the two lists can never quietly drift from what's rendered) -- this one couldn't use the logo/topic-icon trick directly, since `_avatar_html` used to bake a literal hex value into an inline `style=`, and a CSS class has nothing to override there. Switching it to a `avatar-hue-N` class instead (the color lives in `.avatar-hue-N` / `html.theme-b68fbf .avatar-hue-N`, not in the markup) got it onto the same pure-CSS footing as everything else here.
- **An honest-fake progress indicator beats a fake-precise one.** This app has no client-side router -- every navigation here (a nav link, a form submit) is a real full-page reload, so there's no way to know in advance how long any given one will actually take, the same way `/sla`'s own GitHub Actions workflow trigger can't predict its own runtime. `#page-loading-bar` (`loading_bar_script`) doesn't pretend otherwise: it jumps to 20% immediately (so a click always gets instant feedback) then crawls slowly toward, but deliberately never reaches, 100% -- the real navigation's own document teardown is what actually ends the animation, not the bar's own logic hitting a number. It's themed via the existing `--accent` custom property rather than a hardcoded color, so it's already correct under B68FBF (and any future theme) for free. Scope matches what was actually asked for -- every same-tab link and form submit starts it -- with the same-page `#` jump links, `mailto:`/`tel:` links, a modifier-click, and a `target="_blank"` link all deliberately excluded, since none of those actually leave the current page the way this indicator is meant to announce.
- **A row of compact cards should use the width it has, not just the height.** A pass across every page looked at where content was stacking one full-width row per item when each row's own content (a title line plus one row of small fields/buttons) rarely needed the full page width. `/flagged` had already solved this for two named categories side by side (`.two-panel`); the new `.mini-ticket-grid` class generalizes the same idea to a single list of same-shaped rows -- an auto-fill grid (`repeat(auto-fill, minmax(340px, 1fr))`, collapsing to one column under 720px) that the existing `.mini-ticket` row markup drops into unchanged, just gaining a real border on every side (via a higher-specificity descendant rule) instead of the flat list's border-bottom-only look. Both `/tasks`' draft and open lists and `/security`'s read-only list now wrap their rows in it -- `_render_readonly_ticket_row` itself didn't need to change at all, only the container calling it did. On `/sla`, the same "don't stack what could sit side by side" read applied to two different spots: "Week over week" and "Current breaches" (each a handful of short lines in its own full-width box) now share a `.two-panel` row instead of stacking, and the two per-day charts in "Your activity" (which already share one date axis and are meant to be compared) now render side by side in their own `.two-panel` instead of one on top of the other -- both are fluid `viewBox`-based SVGs, so halving their column width just scales them down cleanly, no fixed-pixel-width fix needed. Two smaller companions: the "Add task" form's Category/Estimated-minutes fields gained a `max-width` cap so they stop flex-growing to fill half the form just because there's only one other field next to them, and `/tasks`' "Jump to" links moved into the page's own intro paragraph instead of reserving a full-width row for two short links. `/reconnect` got the opposite treatment on purpose -- it's a genuinely short page (a sentence and a button), and there's no honest content to add to fill it, so `.narrow-page` just caps and centers that small block instead, so the page reads as intentionally compact rather than unfinished.
- **A read-through cache under a multi-threaded server needs the same lock discipline as a write path, not less.** `review_server.py` serves every request on its own thread (`ThreadingHTTPServer`), and this app already guards the two genuinely dangerous double-submit paths against that (`_pending_ticket_action_lock`, `_personal_task_action_lock`) -- but its three read-through Zendesk caches (`_agent_id_cache`, `_security_ticket_cache`, `_flagged_ticket_cache`) had no lock at all, just a plain check-then-act on a module-level dict. Two nearly-simultaneous requests hitting a cold cache could both trigger a live fetch (costly for `fetch_flagged_tickets`, which can page through up to 1,000 tickets); more concretely, `fetch_flagged_tickets` used to `clear()` then `.update()` its cache as two separate steps, so a reader landing in that gap would see a genuinely empty dict mid-refresh -- the Blocked/Standup nav badge flickering to "no badge" even though a fetch was already in flight. Each cache now has its own `threading.Lock()` guarding only the dict read and the dict write -- never the live `get_tickets()`/`search_users()` call itself, the same "don't hold a lock across the slow part" reasoning `update_pending`'s own file lock already uses for `post_comment` -- and `_flagged_ticket_cache` specifically replaced its clear-then-update with one atomic reassignment under that lock, so a reader now always sees either the complete old cache or the complete new one, never a gap between them.
- **A malformed request shouldn't be the one thing in this app that doesn't fail open.** Every `do_POST` branch needing a body used to parse `Content-Length` with a direct `int(self.headers.get("Content-Length", 0))` -- nine duplicated call sites, none guarded. A non-numeric header raised a raw, uncaught `ValueError` straight out of the handler (still isolated to that one request thread by `ThreadingHTTPServer`, but a dropped connection with a server-side traceback instead of this app's usual friendly banner); a negative-but-technically-valid one (`"-1"`) reached `self.rfile.read()` with a negative count, undefined on a socket-backed stream; and a non-UTF-8 body hit the same kind of unguarded raise a step later from `.decode("utf-8")`. All nine call sites now go through one `Handler._parse_form_body()` that catches all three and degrades to an empty form instead -- a request malformed enough to hit any of them was never going to carry usable field values anyway.
- **An invalid escape sequence is a warning today and a `SyntaxError` on a future Python.** `interaction_script`'s embedded JS regex (`/^\[[^\]]*\]\s*/`, from the category auto-fill-onto-subject listener) sat inside a plain Python string, and `\[`/`\]` aren't escape sequences Python recognizes -- harmless today (the backslash just passes through unchanged) but a documented deprecation path ends in that becoming a hard error. Made a raw string (`r"""`) instead, confirmed safe by compiling the whole file with every warning enabled (not just first-occurrence) and finding this the only spot flagged, and confirmed byte-identical rendered output via the existing Playwright suite afterward.
- **Verification that doesn't outlive the session it was written in doesn't protect anything.** Every check built up over this project's development -- personal-task lifecycle, atomic-write/lock correctness, the nav badge caches, all of it -- lived only in an ephemeral scratch environment, gone the moment that session ended. `scripts/tests/` (see "Running tests," above) is a first, deliberately-scoped slice of that made permanent: pure Python, no browser, no real Zendesk credentials, wired into `.github/workflows/tests.yml` so it actually runs on every push and PR instead of once by hand.
- **Two sections answering nearly the same question should be one section, not two.** The main queue page's left-hand **Recently worked on** column (`_render_worked_on_sidebar`, `_common.recent_replied_items`) started out sitting *alongside* the older collapsed **Last N replies** section rather than replacing it, on the reasoning that removing something without checking first is riskier than a bit of redundancy. In practice the two showed nearly identical tickets on any normal day, so `_render_recent_replies` was removed and its one real feature gap from the sidebar -- the confirmed-requester avatar prefix -- got folded into `_render_worked_on_sidebar` instead of being lost. The column also grew from a narrow 220-260px (truncating longer subjects behind an ellipsis, with the full text only reachable via a `title=""` tooltip) to a 300-400px `minmax` that wraps a long subject onto a second line instead -- genuinely showing the full text rather than requiring a hover to find it. Its limit went from 20 to 30 shortly after, once it was clear the fold-in made this the only place that history was visible at all.
- **A "recently worked on" view scoped to only what this tool itself knows about is quietly incomplete the moment you reply to anything directly in Zendesk.** The sidebar above was local-only (`recent_replied_items`) until it became clear that was a real gap, not just a theoretical one -- a reply sent straight from Zendesk's own UI left no trace here at all. `_common.fetch_recently_worked_on` closes that gap the same way `fetch_flagged_tickets`/`fetch_recently_solved_tickets` already handle their own "no direct filter for this" problem: page through the IT-Operations group sorted by `updated_at` (posting any comment bumps it), and for each ticket NOT already in the local history, check its comments for one authored by this tool's own configured account. Two things keep that bounded rather than turning every page load into dozens of extra API calls: a ticket already known locally is never re-checked at all (skipped before any comment fetch happens), and `WORKED_ON_COMMENT_CHECK_LIMIT` caps how many genuinely new candidates get that per-ticket check on a single pass, with the same honest "stopped early" note the other scan-bounded pages use when it's hit. The two sources are just merged and re-sorted by timestamp, not kept visually separate -- a discovered reply and a locally-posted one are the same kind of fact once found, so there's no "via Zendesk" badge distinguishing them beyond how each one was found under the hood.

## Running tests

```
pip install -r requirements-dev.txt
python3 -m pytest scripts/tests/ -v
```

This runs in well under a second, needs no real Zendesk credentials, no network access, and no sibling `zendesk-mcp-server` checkout -- `scripts/tests/conftest.py` puts a trivial stand-in (`scripts/tests/stub_pkg/`) on `sys.path` ahead of the real `zendesk_mcp_server` package, and every test that needs a "client" builds its own small fake one. A `tests/conftest.py` fixture also repoints every one of `_common.py`'s file paths at a fresh temporary directory for each test, so nothing here ever touches this machine's actual `scripts/output/pending_drafts.json`/`personal_tasks.json` -- the real, live data this tool tracks day to day.

What's covered: the personal-task lifecycle (add/edit/reorder/discard and the shared est_mins validation they all route through), the pending-store's and personal-tasks-store's atomic-write-under-an-flock guarantee (exercised with real concurrent writer threads, not just by inspection), the header nav's Blocked/Standup and IT-Security badge caches (staleness lifecycle, the lock added around all three read-through Zendesk caches, and a concurrency smoke test against a slow fake client), and `review_server.py`'s form-body parsing (the malformed/negative Content-Length and invalid-UTF-8 edge cases the audit below found).

What's NOT covered here: anything JS-driven in an actual browser -- the loading bar, theme switching, the category-select auto-fill-onto-subject listener -- or full end-to-end page rendering against a live (fake-client-backed) server. Those remain manual, ad hoc Playwright-based verification during development, the same way they've been built up throughout this project so far; turning a meaningful slice of that into committed, CI-covered browser tests (installing Chromium in the GitHub Actions runner, etc.) is a reasonable next step if it's ever worth the added CI time, but is out of scope for what's committed today. Promote/complete/quick-solve (the personal-task operations that need a live-ish client) aren't covered here yet either, for the same reason -- they remain covered by the ad hoc suite for now.

This suite exists specifically because, before it, every verification script built up over this project's development lived only in an ephemeral scratch environment and never made it into the repo -- meaning none of it actually protected against a future regression once that session ended. `scripts/tests/` is the first slice of that work made permanent and wired into CI.

## Troubleshooting

- `scripts/output/first_reply_check.log` — the cron job's own log, one line per run.
- `scripts/output/review_server.out.log` / `review_server.err.log` — the web server's log (`launchd`'s stdout/stderr capture).
- `scripts/output/watchdog.out.log` / `watchdog.err.log` — the watchdog's own log; `scripts/output/watchdog_state.json` is its "have I already alerted on this" memory between runs.
- If the page won't load, confirm the service is actually running: `launchctl list | grep com.csa`.
- If tickets aren't being detected, check the cron log for "not authenticated" — that's the OAuth token, fixable via the in-page `/reconnect` flow.
- If a refresh reports "N candidate(s) found, 0 new" with nothing new showing up on the page, that's expected, not a bug: `find_candidates()` skips any ticket id already tracked in `pending_drafts.json` (whatever its status), so this message means Zendesk still shows the ticket as `new`/`open` (e.g. you haven't marked it solved yet) but this tool already has a record of it — most commonly because it's already `posted`. Nothing further to do; it'll stop appearing once the ticket itself moves to a status outside `new`/`open` in Zendesk.
- If either service starts throwing `ModuleNotFoundError: No module named 'zendesk_mcp_server'` after a machine restart, the sibling `zendesk-mcp-server` repo's venv has lost track of its own editable install of that package — has happened at least once for reasons that never fully resolved on inspection (its `.pth` pointer file was present and correct, but wasn't being read at interpreter startup regardless). Confirm with `zendesk-mcp-server/.venv/bin/python3 -c "import zendesk_mcp_server"`; if that fails, `.venv/bin/python3 -m pip install -e .` from that repo's root reinstalls it. Both plists now also set `PYTHONPATH` directly at the sibling repo's `src/` as a standing safety net, independent of whether the editable install itself is working, so this specific error shouldn't recur even if that underlying flakiness does.
- After editing and copying a plist into `~/Library/LaunchAgents/`, a "reloaded successfully" message from `launchctl unload`/`load` (what `reload_launchd.sh` used to use) doesn't guarantee the change actually took effect — on at least one Mac this pair silently no-op'd, leaving the OLD definition running. `reload_launchd.sh` now uses `launchctl bootout`/`bootstrap` instead, which doesn't have that failure mode; if you ever reload some other way, prefer those two over `unload`/`load`.
- The watchdog (`watchdog.py`, its own launchd job) checks every 5 minutes whether `review_server` is actually answering HTTP requests and whether `first_reply_check` has completed a scan recently during business hours, and fires a macOS notification the moment either looks stuck — written with zero dependency on `_common.py`/`zendesk_mcp_server` on purpose, so it keeps working even if that exact import chain breaks again. It exists because the `ModuleNotFoundError` above had silently broken both services for an unknown stretch of time before anyone happened to notice the page wouldn't load.
- If `watchdog.err.log` fills with `can't open file '.../watchdog.py': [Errno 1] Operation not permitted`, macOS privacy protection is blocking the watchdog's interpreter from reading `~/Desktop`, so it never runs. This happened with the Command Line Tools `/usr/bin/python3`. The watchdog plist now points at the standalone uv-managed CPython that the other two services already run on (still not the `zendesk-mcp-server` venv). If a `uv` upgrade removes that exact version, update the path in `com.csa.zendesk-watchdog.plist`, copy it into `~/Library/LaunchAgents/`, and reload the watchdog. `watchdog_state.json`'s modification time shows when it last ran.
- `reload_launchd.sh` isn't executable in git, so run it as `zsh scripts/reload_launchd.sh`. If it prints `Bootstrap failed: 5: Input/output error` for one service, check before re-running: the service may have been mid-restart when the script bootstrapped it, and actually be running fine. Check `launchctl list | grep com.csa` (a PID in the first column means it's running) and `curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:8765/`.
